# Phase 4: Wiki as Source of Truth for Fact Data

## Problem

Axiforge currently sources all skill/trait fact data from the GW2 API, then patches it with a static pre-baked `splits.json` generated by a seed script that scrapes the wiki. This creates multiple problems:

- The API frequently omits facts, has missing game mode splits, and stale values
- The seed script reimplements wiki fetching outside of `@axi/gw2-data`, creating duplicate logic
- `splits.json` goes stale between re-seeds
- The merge step (`applyBalanceSplit`) has caused bugs due to fuzzy fact matching
- Multiple patchwork override systems exist to compensate for API gaps

## Solution

Make the GW2 Wiki the authoritative source for all fact values. The API provides structure (what exists, icons, names, descriptions, specialization trees). The wiki provides all fact data (values, durations, coefficients, game mode splits). No merging — wiki facts fully replace API facts when available.

## Architecture

```
GW2 API (/v2/skills, /v2/traits, /v2/professions)
  │
  │  structure: IDs, names, icons, descriptions,
  │  specialization trees, traitedFacts structure
  │
  ▼
catalog.js ◄──── WikiClient.resolveSkillFacts(titles)
  │                    │
  │                    │  values: all fact data per mode
  │                    │  (PvE, WvW, PvP)
  │                    │
  │                    ▼
  │              GW2 Wiki API (batch, 50/request)
  │                    │
  │                    ▼
  │              DiskCache (by ID, 4h TTL)
  │
  ▼
Renderer (receives fully-resolved entities)
```

### Data flow

1. `catalog.js` fetches API skeletons for the profession (skills, traits)
2. Sends API-only catalog to renderer immediately (UI is usable)
3. Kicks off bulk wiki resolution in background
4. Wiki facts arrive per batch → injected onto entities, replacing API facts
5. Incremental IPC updates sent to renderer as batches complete
6. If user opens an entity before its wiki facts arrive, lazy fallback fetches it immediately

## Wiki Client Enhancements

### Batch fetching

Add `getWikitextBatch(titles)` to `WikiClient`:

- Accepts an array of wiki page titles
- Chunks into batches of 50 (MediaWiki API limit per `action=query` request)
- No artificial rate limiting between batches
- Cache-aware: checks cache first, only fetches uncached titles, writes results individually
- Returns `Map<title, wikitext>`

### Fact resolution convenience method

Add `resolveSkillFacts(titles)`:

- Calls `getWikitextBatch(titles)`
- Runs `parseFacts()` on each result
- Returns `Map<title, { facts, hasPveOnly, splitGrouping }>`

### Performance

A profession has ~200 skills + traits. At 50 per batch, that's 4 requests. Cold start: ~1-2 seconds. Warm cache: near-instant.

## Catalog Assembly Changes

### ID-to-title mapping

Each API skill/trait has `id` and `name`. Use `name` as the wiki page title. The wiki API handles redirects natively. Store the `id → title` mapping so wiki results can be keyed back to entities.

### Wiki fact application

For each skill/trait with wiki facts:

1. **Base facts**: wiki-parsed PvE facts become `entity.facts`, fully replacing API facts. No merging.
2. **WvW/PvP facts**: if the wiki page has game mode splits, `entity.wvwFacts` and `entity.pvpFacts` are stored alongside. If no split, those fields are absent (PvE facts apply to all modes).
3. **Icon injection**: wiki facts lack `icon` URLs. Inject icons from the `BOON_CONDITION_ICONS` and `FACT_TYPE_ICONS` constant maps the renderer already maintains. Match by `fact.status` for buff/condition facts, `fact.type` for others.
4. **Traited facts**: keep the API's `traitedFacts` array with its `requires_trait`/`overrides` structure. Each traited fact entry has the same shape as a base fact (type, value fields, etc.). If the wiki page for the skill/trait contains the traited variant's values (e.g. a higher damage coefficient when a specific trait is active), those wiki values replace the API values in the traited fact entry. Match traited facts to wiki data by fact type and position within the traited set. The `requires_trait` and `overrides` metadata fields are always preserved from the API.

### Missing wiki pages

If a skill/trait has no wiki page, log a warning. This indicates a process issue (new skill not yet documented, incorrect title mapping). The entity keeps API-only facts as a last resort, but this should be investigated and fixed.

## Eager Warm-up with Lazy Fallback

### Eager phase

After API skeletons are fetched:

1. Collect all wiki page titles for the profession
2. Fire off `resolveSkillFacts(titles)` in the background
3. As each batch of 50 resolves, update entities and send incremental IPC to renderer
4. Renderer updates its catalog and re-renders if the currently-displayed entity was affected

### Lazy fallback

If the user opens a skill/trait detail before its wiki facts have arrived:

1. Renderer sends `wiki-facts-request` IPC with `{ id, type }` to main process
2. Main process prioritizes that fetch (immediate single-page request)
3. Resolves and sends back via `wiki-facts-resolved` IPC
4. Renderer updates the displayed entity

### IPC messages

- **Main → Renderer**: `wiki-facts-resolved` with `{ updates: [{ id, type: 'skill'|'trait', facts, wvwFacts?, pvpFacts? }] }`
- **Renderer → Main**: `wiki-facts-request` with `{ id, type: 'skill'|'trait' }` (lazy fallback)

## Renderer Changes

### Game mode switching

When the user switches game mode:

- PvE: display `entity.facts`
- WvW: display `entity.wvwFacts` if present, else `entity.facts`
- PvP: display `entity.pvpFacts` if present, else `entity.wvwFacts` if present, else `entity.facts`

### Split highlighting

Instead of the old merge step setting `_splitFact` flags, do a delta comparison at display time. When showing WvW/PvP facts, compare each fact's value fields against the corresponding PvE fact at the same position. If values differ, mark `_splitFact: true` for CSS highlighting. Same visual result, no fuzzy matching.

### Incremental updates

Listen for `wiki-facts-resolved` IPC events:

1. Update the skill/trait in the active catalog
2. If the currently-displayed detail panel shows an affected entity, re-render it
3. No loading spinner needed — facts silently improve from API to wiki values

### Traited facts

`resolveEntityFacts` in `detail-panel.js` continues to work as today. It reads `traitedFacts`, checks active trait IDs, applies overrides/appends with `_traitedFact: true`. The only change is that the values within traited facts are now wiki-sourced.

## Caching

- **DiskCache** in the main process — wiki facts persist across app restarts
- **Cache key by skill/trait ID** — instant lookup during catalog assembly
- **4-hour TTL** — picks up wiki edits within a reasonable window
- **Background refresh** — call `WikiClient.refresh()` on app launch to diff recent wiki changes and invalidate stale entries without re-fetching everything

## Deletion

### Remove `lib/gw2-balance-splits/`

Delete the entire directory:

- `scripts/seed.js` — standalone wiki scraper (replaced by `WikiClient`)
- `data/splits.json` — pre-baked static data (replaced by live wiki reads)
- `match.js` — fuzzy fact matching (no longer needed, no merge step)
- `index.js` — accessor API (`getSkillSplit`, etc.)

### Remove from `catalog.js`

- Delete `applyBalanceSplit` function
- Delete `applyPveFacts` function
- Delete all imports from `lib/gw2-balance-splits`
- Delete `_buildSplitMatchTables` and `_sanitiseUnmatchedSplitFact` helpers

### Fact merger not used

`@axi/gw2-data/facts/merge.js` and `match.js` remain in the package as library code but are not called by the application. Wiki facts fully replace, no merging.

## Testing Strategy

Testing is critical for this phase. Fact values affect every tooltip in the app, and regressions would silently show wrong numbers. Manual smoke testing cannot cover the volume of skills/traits across all professions and game modes.

### Unit tests

- **Wiki client batch fetching**: batching into chunks of 50, cache hit/miss behavior, handling of missing pages, redirect resolution
- **Fact parsing accuracy**: snapshot tests comparing wiki-parsed facts against known-good expected output. Cover all fact types: Damage, Buff, AttributeAdjust, AttributeConversion, ComboField/Finisher, Recharge, Time, Number, Percent, StunBreak, Unblockable
- **Icon injection**: verify all fact types get appropriate icons from constant maps
- **Game mode split separation**: verify PvE/WvW/PvP fact sets are correctly parsed and stored from a single wiki page
- **Split highlighting delta**: verify the comparison logic correctly flags value differences between modes
- **Traited fact wiki resolution**: verify wiki values are applied to traited fact entries while preserving the `requires_trait`/`overrides` structure

### Snapshot/fixture tests

A curated set of ~20-30 real skills/traits across professions that represent the full range of fact patterns:

- Simple damage skills (coefficient, hit count)
- Buff/condition application (duration, stacks)
- Attribute conversions (source, target, percent)
- Healing with coefficients
- Skills with game mode splits (different values in PvE vs WvW)
- Skills with traited facts (overrides and appends)
- Combo field/finisher skills
- Edge cases: multi-hit, channeled, transform skills

Each fixture pins the expected parsed fact output. Tests compare parser output against the pinned expectation. Fixtures are updated deliberately when the parser improves, not silently.

### Integration tests

- Load a real profession catalog through the full pipeline (API skeleton + wiki resolution) and validate:
  - Every skill/trait has facts (no empty arrays unless genuinely factless)
  - All facts have valid `type` fields
  - Buff facts have `status` and `duration`
  - Damage facts have `dmg_multiplier`
  - WvW facts exist where splits are expected
  - Traited facts have valid `requires_trait` IDs and `overrides` indices

### Live validation tests

Extend the existing `real-data.test.js` pattern:

- Run against the actual wiki API (guarded by environment flag, not in CI by default)
- Fetch a representative set of skills/traits and validate:
  - Parser produces non-empty fact arrays
  - Fact types are recognized
  - Value fields are numeric where expected
  - Game mode splits are correctly grouped
- Catch parser regressions when the wiki's template format changes

## Out of Scope

- **Wiki as source for skill/trait discovery** — API still provides the authoritative list of what exists per profession
- **Wiki-sourced icons** — API provides render service icon URLs, wiki doesn't
- **DPS simulation** — the engine computes tooltip values, not rotation DPS
- **Tooltip computation changes** — the engine's `computeTooltip` already works with the fact shape the wiki parser emits
